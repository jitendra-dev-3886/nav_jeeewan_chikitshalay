# Nav Jeevan Chikitsalay

React + TypeScript frontend and Laravel REST backend built from `Nav_Jeevan_Clinic_Technical_SRS.docx` (Phase 1).

The supplied clinic details are included: **Nav Jeevan Chikitsalay / नव जीवन चिकित्सालय**, **Dr. Parmesh Kumar / डॉ परमेश कुमार**, **BAMS, DETCT**, **General Physician and Surgeon**, **Singarjot Ghat, Mahuadhani / सिंगारजोत घाट, महुआधनी**.

## Open the project

The built website is also served directly by Laravel at **http://127.0.0.1:8000** after `npm run build`. The local development website uses **http://127.0.0.1:5173** and staff sign-in uses **http://127.0.0.1:5173/login**. Use `127.0.0.1` consistently so session cookies use the same host.

Double-click **start.cmd** to start both servers, or run `./start.ps1` in PowerShell. Server logs are written to `.local/`. `./stop.ps1` stops processes started by that script.

Local administrator credentials are in **[.local/access.txt](.local/access.txt)**. A random password is generated by local setup; there is no shared default password. Change it under **Users & roles**. This file is ignored by Git and denied by Apache using `.local/.htaccess`.

For a fresh checkout:

```powershell
cd clinic-backend
composer install
Copy-Item .env.example .env
php artisan key:generate
php artisan migrate --seed
php scripts/setup-local.php
cd ../clinic-frontend
npm ci
cd ..
./start.ps1
```

Do not overwrite an existing `.env` when updating the project. `clinic:admin` creates additional administrators interactively:

```powershell
cd clinic-backend
php artisan clinic:admin admin@your-clinic.example
```

## What is implemented

- Responsive homepage, doctor/clinic profile, services and detail pages, FAQs, contact enquiries, health articles, privacy/terms/disclaimer pages, approved testimonials, and gallery.
- Three-step booking with validation, consent, rate limits, timezone-aware slots, duplicate warnings, reference numbers, private expiring management links, rescheduling/cancellation, and calendar download.
- Staff session authentication through Sanctum, CSRF protection, and backend-enforced administrator/receptionist/doctor permissions.
- Dashboard; day/week/list appointment views; search and filters; phone/walk-in entry; controlled status changes; reception notes; appointment history.
- Service and content editing, preview, draft/publish state, weekly availability windows, buffers, slot capacity, daily capacity, booking horizon, lead time, and closure blocks.
- Patient contacts, enquiry assignments/statuses, users and roles, clinic settings, message templates, reports, permission-controlled CSV exports, printable reports, and audit log.
- Validated media uploads, image resizing/WebP conversion, alt text, captions, publication controls, and testimonial consent enforcement.
- Email notification records, database queues, configurable reminders, retry controls, and explicit unconfigured/failed status. No sensitive visit reason or reception notes in messages.
- Page titles/descriptions/canonical links, server-rendered public fallback content when served through Laravel, dynamic XML sitemap, banners, permanent redirects, robots controls, accessible form labels, keyboard focus styles, and reduced-motion support.

Receptionists operate appointments and enquiries. Doctors have read-only schedule access. Administrators manage configuration, content, media, users, reports, and exports. Optional patient OTP login, billing, medical records, prescriptions, payments, telemedicine, waitlists, overbooking, multiple branches, and provider-specific SMS/WhatsApp are not included.

## Banners and clinic logo

**Banners & posters → Add banner / poster** supports text announcements, landscape image banners, and full posters. Upload JPG/PNG/WebP (up to 4 MB), check the preview, and save as draft or publish. Posters are displayed without cropping; image banners fill a wide frame. **Media library** remains available for clinic gallery photos.

Published content refreshes when returning to the page, periodically while it is open, and when an admin saves from another tab on the same origin. Session security tokens are renewed automatically after login, so a manual refresh is not required before saving.

Use **Staff → Banners** to publish announcements in the carousel. It advances every five seconds and reverses at each end; a single published banner also slides back and forth. Controls include arrows, slide indicators, keyboard arrows, swipe, and pause/play. Hover or keyboard focus pauses automatic movement; reduced-motion preferences disable autoplay and animation. Unpublished banners remain hidden.

Use **Staff → Settings → Clinic logo** to upload a JPG, PNG, or WebP logo. Saving updates the header/footer, main clinic feature, doctor page, login, and staff workspace. **Restore original logo** returns to the supplied artwork. Logo changes are administrator-only and audited.

## Database

The running local app uses the dedicated **MySQL database `nav_jeevan_clinic`** on `127.0.0.1:3306`. Connection credentials are stored only in `clinic-backend/.env`. No pre-existing database was changed. The SQLite development database is retained as a fallback. Feature tests and eight-process capacity tests have passed on both SQLite and MySQL. Isolated test databases are named `nav_jeevan_clinic_feature_test` and `nav_jeevan_clinic_concurrency_test`.

For another installation, create a dedicated MySQL 8 database and update `clinic-backend/.env`:

```dotenv
DB_CONNECTION=mysql
DB_HOST=127.0.0.1
DB_PORT=3306
DB_DATABASE=nav_jeevan_clinic
DB_USERNAME=your_clinic_user
DB_PASSWORD=your_password
```

Then run `php artisan config:clear` and `php artisan migrate --seed`. This initializes the MySQL database; it does not transfer SQLite bookings or users. Use `php artisan clinic:admin ...` to create the MySQL administrator. Do not use `migrate:fresh` on clinic data.

Appointments are stored in UTC and shown in Asia/Kolkata. A database transaction locks the existing booking-policy row before slot/capacity checks and writes, preventing the empty-slot race. Changes to services, availability, and closures use the same lock. Appointment duration is the larger of the service duration and schedule slot duration. A cancelled appointment releases capacity; all other statuses consume the original capacity.

## Email and reminders

Configure a real Laravel mail transport in `.env`. The default `log` mailer deliberately records **unconfigured**, rather than pretending to deliver messages or logging patient email content.

```dotenv
MAIL_MAILER=smtp
MAIL_HOST=your_smtp_host
MAIL_PORT=587
MAIL_USERNAME=your_username
MAIL_PASSWORD=your_password
MAIL_FROM_ADDRESS=appointments@your-clinic.example
MAIL_FROM_NAME="Nav Jeevan Chikitsalay"
QUEUE_CONNECTION=database
```

Run separate worker and scheduler processes:

```powershell
php artisan queue:work --tries=3
php artisan schedule:work
```

Production should run the queue worker under a process supervisor and `php artisan schedule:run` every minute via cron. `php artisan clinic:notifications` queues pending updates manually. Monitor Laravel failed jobs and the Notifications screen. “Sent” means the mail transport accepted the message, not that the recipient opened it. Email preference is collected at booking; patients must save the private management link shown after booking. SMS/WhatsApp providers require a chosen provider, credentials, approved templates, and integration testing.

## Validation

```powershell
cd clinic-backend
php artisan test --compact
cd ../clinic-frontend
npm run build
npm run lint
```

`tests/concurrency.py` runs eight independent PHP processes against a disposable SQLite database in `.local/concurrency.sqlite`, expecting one booking and seven conflicts. It refuses to overwrite an existing test database.

`tests/browser-smoke.mjs` uses an already-installed Chrome instance with remote debugging on port 9223. It checks real pages, desktop/mobile overflow, booking progression, field labels, staff authentication/screens, and actual HTTP CSRF enforcement. It requires the two local servers and `.local/access.txt`. Screenshots are saved to `.local/screenshots`. It does not install browser dependencies or submit live patient bookings.

See [docs/SRS-coverage.md](docs/SRS-coverage.md) for requirements and [docs/deployment.md](docs/deployment.md) for launch and backup procedures.
